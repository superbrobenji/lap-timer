# Lap Timer Implementation Roadmap

**Spec:** `docs/superpowers/specs/2026-09-14-lap-timer-design.md`
**Date:** 2026-09-14

Work is organised by hardware availability, then into **day-sized sessions**. One session = one sitting, 3–5 bite-sized tasks, a green test run, a commit, and a tag. No agent run spans more than one session. Each session either has its task list in an existing plan document (plan 1) or gets its own short plan document written at the start of that session (`plan-NN-dD-<topic>.md`), so the plan can reference the real code that exists by then.

## Session protocol

1. **Start:** read the spec sections named for the session; for plans ≥ 2 write the session's plan document with the writing-plans skill (tasks, code, tests) and commit it.
2. **Execute:** subagent-driven, one fresh subagent per task, review between tasks. Stay inside the session's task list; discoveries that change the spec are written back into the spec in the same commit.
3. **Finish:** `ctest` green (and the bench check for firmware sessions). A gcc parity build must also be green before the PR (CI runs gcc on ubuntu, the host runs clang): `CC=$(ls /opt/homebrew/bin/gcc-* | head -1) cmake -S test -B test/build-gcc -DCMAKE_BUILD_TYPE=Debug && cmake --build test/build-gcc && ctest --test-dir test/build-gcc --output-on-failure`. Run the hygiene check locally too: `git diff --check $(git hash-object -t tree /dev/null) HEAD -- . ':!*.pbm' ':!*.bin' ':!components/core/include/core/jsmn.h'` must print nothing. Work lives on a session branch `s<plan>.<day>-<topic>`; open a PR with `gh pr create --base main --title "..." --body-file .github/PULL_REQUEST_TEMPLATE.md`, wait for the five required checks, squash-merge, then tag `pNN-dD` on `main` and push the tag. Any change that adds or renames a firmware matrix environment must update the branch-protection required checks in the same PR (`gh api -X PATCH repos/superbrobenji/lap-timer/branches/main/protection/required_status_checks`). Note any leftover in the next session's entry criteria rather than running over.
4. **Deferred minors:** a review finding that is parked instead of fixed is filed as a GitHub issue the same day, naming the session that owns it. A plan's last session runs the whole-plan review (opus) plus one fix wave and closes every issue owned by that plan before `plan-NN-done`; an issue that must move to a later plan is re-owned explicitly in its body.

## Plan 4.5 — Power of 10 compliance (before Plan 5)

Spec: `docs/superpowers/specs/2026-09-17-power-of-10-compliance-design.md`. Strict adoption of the NASA/JPL Power of 10 rules on the shipped on-device C (`components/core`/`app`/`drivers`, `main`); host `tools`/`test` exempt but zero-warning; vendored/IDF exempt. Strict + adversarially-justified deviation register (burden of proof on every exception). Behavior-preserving retrofit. Rule 9 (function pointers) is done LAST. Follows Holzmann's **refined** rule forms (`spinroot.com/p10`), adopted mid-plan on 2026-09-19: refined rule 5 (≥2 assertions per function >20 lines, small functions exempt, no padding), rule 4's 30-line compound-statement gate, rule 6 static-linkage, and rule 8's `#undef`/logic-macro gates — see design §3.

| Session | Scope | Spec | Exit criteria |
|---------|-------|------|---------------|
| 4.5.1 | tooling: `clang-tidy` + `cppcheck` + custom linter (`tools/lint/power_of_10.py`) wired into CI report-only; `docs/power-of-10-deviations.md` register skeleton; app-layer `LT_ASSERT_*` over the core assert hook | §2,§5,§4 | the three analysers run as report-only CI jobs; register + macro exist; zero behavior change; tag `p4.5-d1` |
