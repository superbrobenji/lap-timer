# Plan 4.5: Power of 10 Compliance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax. Sessions 4.5.2–4.5.6 are appended to this document at the start of each session (like plans 02–04), once the tooling and prior retrofits they build on exist.

**Goal:** Bring the shipped on-device firmware C into strict compliance with the ten rules of Power of 10 (Holzmann/JPL) and keep it compliant, via CI static analysis and an adversarially-justified deviation register — behavior-preserving throughout.

**Architecture:** A custom text linter (`tools/lint/power_of_10.py`) enforces the project-specific gates (function length, assertion density, no heap after init, no unregistered function pointer, restricted preprocessor) directly on the source; `clang-tidy` (over the IDF and host compile databases) and `cppcheck` add the deeper control-flow/pointer/return-value checks (rules 1/6/7/9 and "multiple analysers"). All three run report-only in CI while the retrofit lands, then flip to blocking required checks. The retrofit changes only *how* code is written; the existing host tests, `core_selftest` on the ESP32, the PBM UI goldens, the replay fixtures, and the on-device measurements are the regression net.

**Tech Stack:** ESP-IDF v5.3.2 (built via `tools/idf-env.sh`), C11, the host test harness (Unity, clang `test/build` + gcc-16 `test/build-gcc`), `clang-tidy`/`cppcheck` (CI), Python 3 (the linter). No new firmware dependency.

**Spec:** `docs/superpowers/specs/2026-09-17-power-of-10-compliance-design.md` — the authority for the rule interpretations, the scope, the strict+adversarial-deviation model, and the delivery order (rule 9 last). Read it before any task.

## Global Constraints

- **Scope of the rules:** `components/core/**`, `components/app/**`, `components/drivers/**`, `main/**` (the shipped on-device C) obey all ten rules per the design §3. `tools/**` and `test/**` are exempt from the ten rules but MUST stay zero-warning (rule 10). Vendored / managed / ESP-IDF code is fully exempt: `test/unity/**`, `components/core/util/jsmn*`, `managed_components/**`, and anything under `$IDF_PATH`.
- **Behavior-preserving:** no interface change, no behavior change, no feature change ships in this plan. Every session keeps the full existing test suite, the PBM goldens, the replay fixtures, and (for firmware sessions) the on-device behavior identical. A firmware session flashes the affected env to confirm (the standing build-and-flash rule; wait for the user's "ready").
- **Deviation burden of proof (design §2):** a function pointer or other exception is registered in `docs/power-of-10-deviations.md` only after a spelled-out compliant alternative is shown to genuinely fail or clearly not be worth its cost. Default is comply. The register row records the rejected alternative, not just a justification.
- **Rule 4:** ≤ 60 lines of code per function (blank, comment-only, and brace-only lines excluded).
- **Rule 5:** per-component average ≥ 2 assertions/function via `CORE_ASSERT_RET`/`CORE_ASSERT_VOID` (core) or `LT_ASSERT_RET`/`LT_ASSERT_VOID` (app/drivers/main), over the `core_set_assert_hook` reporter — log to the §17.7 error ring and return a safe value, NEVER abort on the device. Assertions check real anomalies, are side-effect-free.
- **Rule 9 is done LAST** (session 4.5.5); the linter's no-unregistered-function-pointer gate stays inert until then.
- **Existing build flags stay:** `-Wall -Wextra -Werror -Wshadow` + `-Wconversion` (non-fatal), ASan/UBSan on host — the analysers add to, never replace, these.
- **Subagent models:** never dispatch a subagent on Fable; haiku/sonnet/opus by task tier.

### Task 1: the custom linter + deviation register + `LT_ASSERT_*`

**Files:** create `tools/lint/power_of_10.py`, `docs/power-of-10-deviations.md`, `components/app/include/app/lt_assert.h`. No source edits under `components/**`/`main/**`.

**Interfaces produced:**
- `tools/lint/power_of_10.py [--paths ...] [--register docs/power-of-10-deviations.md] [--enforce-fnptr] [--json]` — scans the in-scope C (default: `components/core components/app components/drivers main`, excluding the vendored/exempt paths in the design §1). Checks, each reporting `file:line: RULE-N: <msg>`:
  - **rule 4** function length > 60 code lines (exclude blank/comment-only/brace-only lines; count from the `{` of a top-level function definition to its matching `}`);
  - **rule 5** per-component (per top-level dir) average assertions/function < 2 (count `CORE_ASSERT_*`/`LT_ASSERT_*` calls ÷ function count; report the average, not per-function);
  - **rule 3** any `\b(malloc|calloc|realloc|free|strdup|aligned_alloc)\s*\(` in in-scope code (heap);
  - **rule 8** `##` token-paste or `#<ident>` stringisation-as-logic in in-scope code (allow it inside the exempt X-macro/test paths);
  - **rule 9** (only when `--enforce-fnptr`) a function-pointer typedef/parameter/variable whose `file:symbol` is not in the register — INERT by default this session.
  It reads the register (skips registered sites), prints a summary, and exits non-zero only when a NON-report-only invocation finds an unregistered violation. Default mode is report-only (always exit 0, print findings). Pure-Python, no third-party deps.
- `docs/power-of-10-deviations.md` — the design §4 table (`id | rule | file:symbol | compliant alternative considered | why rejected | benefit | reviewer`), seeded with ONLY the genuinely-unavoidable IDF/FreeRTOS boundary function pointers (task entry `xTaskCreateStatic*`, `gpio_isr_handler_add`/`board_buttons_enable_isr` handler, `esp_timer` callbacks) — each row's "why rejected" = "the IDF/FreeRTOS API signature is a function pointer; no compliant alternative without abandoning the SDK". The codebase's own callbacks are NOT seeded (they are reworked in 4.5.5, not registered).
- `components/app/include/app/lt_assert.h` — `LT_ASSERT_RET(cond, code, ret)` / `LT_ASSERT_VOID(cond, code)`, mirroring `core/core.h`'s macros but callable from the app/driver layer (which may not include `core/core.h` directly): they call the same `core_assert_fail(code, __FILE__, __LINE__)` reporter (so app assertions land in the §17.7 error ring via the installed hook) and `return (ret)` / `return`. No behavior change (nothing calls them yet).

## Session 4.5.2 — retrofit `components/core` to rules 1–8, 10 (behavior-preserving)

Roadmap exit: the core linter reports clean (avg assertions ≥ 2, 0 functions > 60 code lines, 0 heap/preprocessor); host tests + `core_selftest` green on the ESP32; tag `p4.5-d2`. PARALLEL: a worktree wave of 4 disjoint sub-component tasks, then serial integration. Function pointers are LEFT untouched (rule 9 is 4.5.5).

**Shared retrofit contract (every task, every file it touches):**
- **Behavior-preserving. No interface change, no logic change.** Only: split over-length functions into named static helpers; add assertions; bound loops; make return-value handling explicit; tighten scope. The existing host tests and the replay fixtures must stay byte-for-byte green — that is the proof of no regression.
- **Rule 4:** any function > 60 code lines (blank/comment/brace-only excluded) is split into named `static` helpers with clear responsibilities. The 4 core offenders: `fus_step` (fusion), `lap_on_fix` (lapengine, 109 lines), `drag_on_fused` (dragengine), `exp_json_feed` (export).
- **Rule 5:** raise assertion density so the FILES THE TASK TOUCHES average ≥ 2 assertions/function (so the whole `components/core` averages ≥ 2). Use `CORE_ASSERT_RET(cond, code, ret)` / `CORE_ASSERT_VOID(cond, code)` (`core/core.h`). Assert REAL anomalies only — pointer params non-NULL, array indices/counts in range, enum/state values valid, numeric ranges the function assumes, key postconditions/invariants. NEVER tautologies (`CORE_ASSERT(x==x)`), never a condition with a side effect, never a check the types already guarantee. Trivial one-line accessors may carry zero — the density comes from the substantive functions. Pick a plausible `code` from `core/err.h`/§17.7 (or the nearest existing code); do not invent a behavior. A failing assertion reports + returns a safe value (it must NOT change the success-path behavior the tests observe).
- **Rule 2:** every loop has a statically evident bound. Where a `while`/scan loop is not already bounded by a fixed capacity, add an explicit iteration cap (`for (int i = 0; i < CAP && ...; i++)`) sized to the real maximum, with a `CORE_ASSERT` if the cap is hit.
- **Rule 7:** every non-`void` call result is used or explicitly `(void)`-cast with intent; parameter validation is the rule-5 assertions.
- **Rules 6/1/8:** narrow any over-broad scope; no recursion/goto (none expected); no new complex macros.
- **Generated/data files are exempt:** `components/core/ui/fonts.c` is generated glyph data (source is `tools/fonts/gen_fonts.py`) and `icons.c` is hand-authored bitmap data — do not add assertions to the data tables; add the fonts.c path to the linter's exempt list (integration step). `jsmn` is already exempt.
- **Verify per task:** build the host test tree (`cmake --build test/build && ctest --test-dir test/build`) green for the areas the task's files feed; run `python3 tools/lint/power_of_10.py --paths <the task's dirs>` and confirm its files hit avg ≥ 2 and 0 over-length.
